# 1강에 앞서, 사전지식 : Vite로 React 프로젝트 만들기

## 선행 준비 (PC에 필요한 것)

- **Node.js** (LTS 권장): [https://nodejs.org](https://nodejs.org) 에서 설치합니다.
- 터미널에서 아래처럼 버전이 나오면 준비가 된 것입니다.

```bash
node -v
npm -v
```

- 위에서 **`command not found`** 가 나오면 Node가 없거나 PATH에 잡히지 않은 경우가 많습니다. **macOS** 기준 설치 예시는 아래와 같습니다.
- **npm은 별도 설치가 보통 필요 없습니다.** [nodejs.org](https://nodejs.org) **공식 LTS** 패키지와 **`brew install node`** 모두 **npm을 Node와 함께** 설치합니다. (`node -v`가 되면 `npm -v`도 같이 되는 것이 정상입니다.)

**방법 1 — 공식 설치 프로그램**

- 앞 문단의 [https://nodejs.org](https://nodejs.org) 에서 **LTS** 설치 파일(`.pkg`)을 받아 실행합니다.

**방법 2 — Homebrew** (`brew`가 이미 있을 때)

```bash
brew install node
```

**Homebrew가 없을 때** (Apple Silicon / Intel 공통, [brew.sh](https://brew.sh) 안내와 동일)

```bash
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
```

설치가 끝나면 터미널을 다시 열고 `node -v`, `npm -v`로 다시 확인합니다.

- **`node`는 되는데 `npm`만 없거나 오류**인 경우는 드뭅니다. 먼저 터미널을 완전히 종료했다가 다시 열고, 그래도 같으면 **Node를 동일한 방식으로 다시 설치**하는 것이 가장 단순합니다.
- 그래도 **npm만 복구**해야 한다면(이미 `node` 명령은 정상일 때), npm에서 제공하는 설치 스크립트를 쓸 수 있습니다. 터미널 안내(관리자 권한 등)를 따릅니다.

```bash
curl -L https://www.npmjs.com/install.sh | sh
```

[Vite](https://vitejs.dev/)는 개발 서버와 빌드(배포용 파일 만들기)를 빠르게 해 주는 도구입니다. React 공식 문서에서도 권장하는 시작 방법 중 하나입니다.

### 1) 새 프로젝트 생성

터미널에서 **만들 폴더의 상위 위치**로 이동한 뒤, 아래를 실행합니다.

```bash
npm create vite@latest lesson-01-static-jsx -- --template react
```

- `lesson-01-static-jsx` 부분은 **프로젝트 폴더 이름**입니다. 원하는 이름으로 바꿔도 됩니다.
- `--template react` 는 **JavaScript + React** 템플릿을 고르는 옵션입니다. (TypeScript가 아닌 JS로 시작할 때)
- `--template react-ts` 로 변경하면 TypeScript로 템플릿을 만들게 됨
- 위의 bash 명령에서 중간에 위치한 -- 의 역할은 “앞은 npm이 해석하고, 뒤는 npm이 건드리지 말고 전부 하위 명령(create-vite)에 넘겨라”라는 구분자입니다.
- npm은 vite@latest, 폴더 이름 lesson-01-static-jsx까지만 자기 쪽 옵션으로 보고,
- 그 다음부터(--template react)는 create-vite 실행 파일이 받는 인자로 그대로 전달됩니다.
- 만약 --가 없으면 npm이 --template을 자기 옵션으로 오해하거나, 넘기는 방식이 달라질 수 있어서, 이런 래퍼 명령에서 자주 씁니다.

> **참고:** `npm create vite@latest` 만 실행하면, 터미널이 프로젝트 이름·프레임워크(React)·변형(JavaScript/TypeScript)을 **대화형으로 물어봅니다.** 위 한 줄 명령은 그 과정을 건너뛰고 바로 같은 결과에 가깝게 만드는 방식입니다. 

> **보충 — Vite는 React 전용 도구가 아닙니다**  
> Vite는 웹 프론트엔드용 **개발 서버**(로컬에서 빠르게 미리보기)와 **번들러**(배포용으로 파일 묶기) 역할을 합니다. React/Vue 등 **프론트엔드 프레임워크를 쓸지**, 혹은 아예 안 쓰고 **Vanilla**로 갈지는 **프로젝트 설정·플러그인**으로 정합니다.
>
> 처음에는 Vite가 하는 일을 **두 영역**으로 나누어 보면 이해하기 쉽습니다.
>
> **① JavaScript / TypeScript 분야: 코드 빌드**  
>
> - 우리가 작성하는 `*.js`, `*.jsx`, `*.ts`, `*.tsx`를 브라우저가 실행할 수 있게 **의존성 있는 패키지들을 묶고 순수 JS로 변환**하는 흐름이 여기에 해당합니다.  
> - `npm create vite`의 **템플릿**(Vanilla, Vue, React, Preact, Lit, Svelte 등)을 고르면, **시작 코드와 폴더 구조**가 프레임워크마다 달라집니다. (같은 “Vite”라도 안에 들어가는 **앱 코드 종류**가 다른 셈입니다.)
>
> **② 스타일(CSS) 분야: 모양 빌드**
>
> 같은 “스타일”도 **역할이 다른 두 갈래**로 나누어 읽습니다.
>
> - **한눈에 비교**
>   - **Vite–PostCSS 계열 (예: Tailwind)**  
>     - **직관:** 스타일을 `***.module.css`에 직접 `padding: …`처럼 CSS코드를 쓰지 않아도**, JSX에 `className="flex gap-2"`처럼 **유틸 이름만 선언형으로** 나열하는 쪽에 가깝다. (긴 규칙은 빌드가 소스를 보고 만들어 낸다.)  
>     - **빌드가 하는 일:** `import`한 CSS 문자열을 **프로세서 `postcss`**가 받아, `postcss.config.js` 등에 설정된 **플러그인**(예: `tailwindcss`, `autoprefixer`)을 **순서대로** 적용해 **브라우저에 줄 최종 CSS**로 생성해낸다.
>   - **CSS Modules 계열**  
>     - **직관:** `**Button.module.css` 안에** `.primary { … }`처럼 **CSS 규칙을 내가 직접 코드로** 적는다. 그다음 `**Button.jsx` 등 그 스타일을 쓰는 JS/JSX 파일**에서 `import styles from './Button.module.css'` 후 `className={styles.primary}`처럼 붙인다. (꼭 `main.jsx` **한 군데**가 아니라, 내가 구현하는 **컴포넌트마다** import하는 경우가 많다.)  
>     - **빌드가 하는 일:** `.module.css`에 적어 둔 **클래스 이름**을 빌드 시 **파일마다 다른 고유 이름으로 바꿔** 전역에서 안 부딪히게 한다. (**PostCSS가 “규칙을 새로 생성”하는 주역이라기보다, “이름 격리”가 핵심.** 맡는 일이 위와 다름.)
>   - `**npm create vite@latest … --template react` 직후 (추가 설정)**  
>     - **Vite–PostCSS 계열 (예: Tailwind):** 기본 템플릿에는 **들어 있지 않다.** 아래는 **Tailwind v4 + React + Vite** 기준으로, [공식 “Tailwind with Vite” 설치](https://tailwindcss.com/docs/installation/using-vite)와 맞춘 4단계 절차다. (`npm create vite` 대화형에서 Tailwind를 고를 수 있는 경우도 있으나 **항상 자동은 아니다.**)  
>       - **1) 프로젝트 폴더로 이동 후 패키지 설치**
>         ```bash
>         cd lesson-01-static-jsx   
>         npm install tailwindcss @tailwindcss/vite 
>         # 위의 명령에서 tailwindcss는 유틸 클래스를 만들어 내는 Tailwind 본체(엔진·설계) 
>         # 뒤에 있는 @tailwindcss/vite는 Vite가 npm run dev / npm run build 할 때, 그 과정 안에서 Tailwind가 CSS를 처리·생성하도록 연결하는 “Vite용 어댑터” 역할입니다.
>         ```
>       - **2) `vite.config.js`에 Vite용 Tailwind 플러그인 등록** — 기존 `react()` 플러그인은 유지하고 `tailwindcss()`를 같이 넣는다.
>         ```js
>         import { defineConfig } from 'vite'
>         import react from '@vitejs/plugin-react'
>         // 아래 부분을 삽입한다.
>         import tailwindcss from '@tailwindcss/vite'
>
>         export default defineConfig({
>           plugins: [react(), tailwindcss()],
>         })
>         ```
>       - **3) 진입 CSS에 Tailwind 한 번 불러오기** — Vite React 템플릿은 보통 `src/main.jsx`가 `import './index.css'`를 이미 하고 있으므로, `**src/index.css` 맨 위**에 아래 한 줄을 둔다. (템플릿에 있던 데모용 규칙은 유지·삭제·합치기는 프로젝트에 맞게 정리하면 된다.)
>         ```css
>         @import "tailwindcss";
>         ```
>       - **4) 개발 서버 실행 후 JSX에서 유틸 클래스 사용** — `npm run dev`로 띄운 뒤, 예를 들어 컴포넌트에서 `className="flex gap-2 rounded-lg p-3"`처럼 쓴다.  
>       - **참고 (구버전·다른 튜토리얼):** 예전 방식은 `postcss`·`autoprefixer`를 함께 설치하고 `postcss.config.js`·`tailwind.config.js`의 `content`를 맞춘 뒤, CSS에 `@tailwind base;` / `@tailwind components;` / `@tailwind utilities;`를 쓰는 **Tailwind v3 + PostCSS** 경로였다. 이 문서 **뒤쪽「### B. Tailwind…」예시 코드**가 그 형태에 가깝다. **새 프로젝트**는 위 **v4 + `@tailwindcss/vite`** 흐름이 공식 문서 기준에 맞다.
>     - **CSS Modules (`*.module.css`):** **추가 설정 없이** 쓸 수 있다. 파일명이 `*.module.css`이면 Vite가 CSS Modules로 처리하고, 컴포넌트에서 `import styles from '…'`만 하면 된다.
> - **질문:** Tailwind(Vite–PostCSS) 쪽도 **이렇게 고유 이름으로 바꿔 격리**해야 하나?  
>   - **답:** **유틸만 쓰는 전형적인 방식**에서는 보통 **그럴 필요가 없다.** `flex`, `p-4` 같은 이름은 **프레임워크가 정한 전역 유틸**이라, 컴포넌트 A와 B가 같은 `className="flex"`를 써도 **의도적으로 같은 규칙을 공유**하는 모델이다. CSS Modules가 다루는 문제는 **내가 지은 `.title`, `.primary`가 파일마다 다른데 전역 네임스페이스는 하나**라서 생기는 **충돌**에 가깝다.  
>   - **주의:** Tailwind를 쓰더라도 `**@layer`나 별도 CSS에 `.card`처럼 직접 지은 클래스**를 여러 파일에서 겹쳐 쓰면 **전역 충돌은 여전히** 날 수 있다. 그때는 이름을 다르게 짓거나, CSS Modules·스코프 전략을 쓰는 식으로 다룬다.
>
> ---
>
> ### 스타일(CSS) 분야: 모양 빌드 --> 2가지 방식 상세 비교
>
> **A. Vite–PostCSS 계열 (Tailwind를 예로 들면)**
>
> - **① npm에서 오는 것**  
>   - `tailwindcss` 등은 “이미 완성된 **최종 CSS 한 장**”이 아니라, **유틸 규칙을 만들 엔진·설계(테마 등)** 에 가깝다.
> - **② 내가 소스에 쓰는 것**  
>   - JSX의 `className="flex p-4"`에서 `flex`, `p-4`는 **패키지가 넣어 주는 게 아니라 내가 적는 문자열**이고, Tailwind가 정의한 **유틸리티 이름**이다. 이렇게 선언만 해주면 되고, 구체적으로 정의를 하지 않아도 된다.  PostCSS·`tailwindcss` 플러그인이 자동으로 해주니까.   
>   - 빌드가 프로젝트 소스를 훑어 **실제로 쓰인 이름만** 골라 CSS 규칙을 만든다.
> - **③ CSS 파일 연결**  
>   - `main.jsx`에서 `import './index.css'` (Vite 템플릿에서는 보통 `index.css`)로 **한 CSS 파일**을 붙인다.  
>   - 그 안에 `@tailwind base;` 등 지시문을 두면, PostCSS·`tailwindcss` 플러그인이 이를 **펼쳐서** 최종 CSS로 만든다.
> - **④ 누가 무엇을 하나**  
>   - `**postcss` 패키지:** CSS 문자열을 받아 **플러그인을 순서대로** 도는 **프로세서**.  
>   - `**tailwindcss` 플러그인:** 위 ②·③을 바탕으로 **규칙 생성**에 큰 몫.  
>   - **Vite:** PostCSS를 새로 짠 게 아니라, `import`한 CSS를 만날 때 `**postcss`를 호출**해 결과를 번들에 넣는 **번들러·개발 서버**. (`postcss.config.js` 등이 있으면 dev·build에서 이 단계가 빠지지 않게 이어 준다.)
> - **⑤ 다른 문법 (참고)**  
>   - **Sass/SCSS·Less**는 브라우저가 바로 못 읽을 수 있어, 빌드에서 **일반 CSS로 바꾸는** 단계가 있다. (보통 같은 **스타일 파이프라인** 안에서 처리.)
> - **⑥ shadcn/ui (참고)**  
>   - CSS 엔진이 아니라 **복사해 쓰는 React UI 조각**(보통 Tailwind 기반). Tailwind와 **같은 파이프라인**을 쓸 뿐, shadcn **전용 Vite 모드**가 생기는 것은 아니다.  
>   - “컴포넌트 패키지 + 스타일 패키지를 따로 깐다”는 그림은 **shadcn 쪽**에 더 가깝고, Tailwind만 쓸 때는 **JSX 클래스 문자열 + 설정 + `main`에서 import하는 CSS**가 중심이다.
>
> ---
>
> **B. CSS Modules 계열 (`*.module.css`)**
>
> - **① 무엇을 해결하나**  
>   - 일반 CSS 클래스는 **전역**이라, 여러 파일에 `.title`이 있으면 스타일이 섞일 수 있다.
> - **② 내가 쓰는 것**  
>   - `Button.module.css`에 `.primary { … }`처럼 **직접 규칙을 쓴다.**
> - **③ JS와 연결**  
>   - `import styles from './Button.module.css'` 후 `className={styles.primary}`처럼 붙인다.
> - **④ 빌드가 하는 일**  
>   - `primary` 같은 이름을 **파일마다 다른 고유 클래스명**(예: `Button_primary_a3f2`)으로 바꿔 **이름 충돌을 막는다.** (말로는 “파일 단위로 클래스를 묶는다”고도 한다.)
> - **⑤ PostCSS와 겹칠 때**  
>   - 같은 `.css`가 PostCSS도 거치면 **추가 가공**은 겹칠 수 있지만, **Modules의 본질은 ‘이름 격리’** 이다.
>
> ---
>
> **양쪽 차이만 다시 정리**
>
> - **Tailwind 쪽:** 마크업에 **짧은 유틸 이름**을 많이 적고, **규칙은 빌드가 만들어 내는** 쪽에 가깝다.  
> - **CSS Modules 쪽:** `**.module.css`에 규칙을 직접** 쓰고, 빌드는 주로 **이름만 바꿔** 스코프를 나눈다.  
> - 둘 다 “CSS를 손본다”는 말로 한꺼번에 묶으면 헷갈리므로, **위 A / B**처럼 나누어 기억하면 된다.

## 코드로 보는 스타일 두 갈래 (참고 예시)

**실행 화면:** `src/App.jsx`는 같은 `**Header`·`MenuCard`** 에 `variant` prop만 바꿔 **일반 CSS / CSS Modules / Tailwind(웜톤) / shadcn/ui(Card + Toolbar + Radix Dialog)** 네 열을 한 화면에 띄운다(`npm run dev`). 컴포넌트 마크업은 동일하고 **className만** 방식·톤별로 달라진다. **C열과 D열은 둘 다 Tailwind 파이프라인**을 타지만, D열은 추가로 `Button`/`Input`/`Badge`/`DropdownMenu` 조합과 Radix Dialog 기능(열기/닫기/ESC/포커스 관리)을 함께 보여 준다. 즉 D열은 `src/components/ui/card.jsx` + `src/components/ui/button.jsx` + `src/components/ui/input.jsx` + `src/components/ui/badge.jsx` + `src/components/ui/dropdown-menu.jsx` + `src/components/ui/dialog.jsx` + `src/lib/utils.js`(`cn`)를 함께 import해 쓰는 구조다.

아래 절 **A·B·C**는 그중 **전역 / 모듈 / 유틸** 세 축을 **코드 조각으로** 다시 읽기 위한 참고이며, 폴더 `examples/`에는 **짧은 보조 스니펫**만 따로 두었다. **C·D** 모두 Tailwind 유틸이므로 `**tailwindcss` + `@tailwindcss/vite` 설치** 후에 스타일이 적용된다.

### `variant` prop — 무엇이고, 왜 쓰는가

이 레슨의 `**Header`**, `**MenuCard**`, 그리고 `App.jsx` 안의 `**MenuGrid**`(메뉴 카드를 감싸는 그리드 래퍼)는 공통으로 `**variant**` 라는 **문자열 prop**을 받을 수 있다.  
**React가 제공하는 특별한 속성이 아니다.** 이 프로젝트에서만 약속한 이름이며, **“스타일을 어떤 방식으로 입힐지”** 를 고르는 스위치 역할이다.


| `variant` 값              | 의미                                                                                                               | `className`이 어떻게 정해지는가                                                                                                                        |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- |
| default (A안: 생략 시 이 값) | src/index.css 에 적어 둔 **전역 클래스**를 쓴다.                                                                       | 예: `className="muted"`, `className="card"` — 브라우저에 올라가는 클래스 문자열은 개발자가 적은 그대로(전역 네임스페이스).                                                      |
| css-modules  (B안) | 같은 모양을 *.module.css 안에 규칙으로 적고, 빌드가 클래스명을 파일마다 고유하게 바꾼다.                                                   | 예: `className={styles.card}` — `styles`는 import 한 모듈 객체이며, **실제 DOM에는 해시가 붙은 클래스명**이 찍힌다.                                                     |
| tailwind    (C안)  | Tailwind 유틸 문자열을 `className`에 나열한다(이 레슨에서는 **웜톤·카페**에 맞춘 stone/베이지).                                         | 예: `className="rounded-lg border-stone-200 …"` — 유틸 이름은 개발자가 적고, **최종 CSS 규칙은 Tailwind + Vite 파이프라인이 생성**한다.                                  |
| shadcn    (D안)  | src/components/ui/*의 **조립형 UI 컴포넌트**(Card/Button/Input/Badge/Dropdown/Dialog)를 import해 쓴다(스타일은 Tailwind 유틸 기반). | 실무에서는 보통 `npx shadcn`으로 파일을 생성한 뒤, 프로젝트 내부에서 직접 수정·확장하며 사용한다. 이 레슨도 같은 구조(`components.json`, `src/components/ui/*`, `src/lib/utils.js`)를 갖춘다. |


**컴포넌트 안에서는 어떻게 나뉘나**

- `Header.jsx` / `MenuCard.jsx`는 내부에서 `**variant` 값에 따라** `if` 분기로 **같은 태그 구조**를 유지한 채, **분기마다 다른 `className`만** 붙인다(`css-modules` → `tailwind` → `shadcn` → 그 외 `default` 순 등).  
즉 **마크업(태그·자식 구조)은 같고**, **스타일이 붙는 방식·톤**이 네 갈래로 나뉜다.
- `**MenuGrid`**는 네 열 모두에서 **같은 자식(`MenuCard` 두 개)** 을 받되, 그리드 자체의 스타일만 다르게 한다.  
  - `default` → 전역 `.menu-grid`  
  - `css-modules` → `CompareLayout.module.css`의 `.menuGrid`  
  - `tailwind` → `className="grid gap-3 mt-4"`  
  - `shadcn` → `className="grid gap-4 mt-5"` (간격만 살짝 다르게 해 두어 D열을 구분하기 쉽게)

**실무에서 이런 `if (...) return (...)` 패턴을 많이 쓰나?**

- **자주 쓴다.** 특히 `variant`가 2~4개 정도이고, 분기마다 마크업이나 클래스 묶음이 눈에 띄게 다를 때는 조기 `return`이 가장 읽기 쉽다.
- 다만 분기가 계속 늘어나면 한 컴포넌트가 길어지므로, 그때는 `switch`/매핑 객체/하위 컴포넌트 분리(`MenuCardTailwind`, `MenuCardShadcn`) 같은 방식으로 리팩터링하는 편이 유지보수에 유리하다.
- 기준은 단순하다: **지금 읽기 쉬운가? 앞으로 늘어날 가능성이 큰가?** 이 두 가지를 보고 선택하면 된다.

`**App.jsx`의 `map()`은 무엇을 하는가?**

- `map()`은 **배열의 각 원소를 순회해서, 같은 개수의 새 배열을 만드는 JavaScript 메서드**다.
- React JSX에서는 이 새 배열이 보통 **컴포넌트 목록(반복 렌더링 결과)** 이 된다.
- 이 레슨에서는 `map()`이 두 번 쓰인다.
  - `variants.map(...)` → **스타일 비교 열(`section`) 4개**를 만든다.
  - `DEMO_MENUS.map(...)` → 각 열 안의 **메뉴 카드(`MenuCard`) 2개**를 만든다.
- 즉 “스타일 분기(`if`)”는 **한 카드의 모양을 고르는 일**이고, “`map()`”은 **그 카드/열을 데이터 개수만큼 찍어내는 일**이다.
- 실무에서도 반복 UI는 거의 항상 `map()`으로 렌더링하며, 이때 `key`를 안정적으로 주는 습관이 중요하다(이 코드에서는 `section`에 `key={v}`, 카드에 `key={item.name}` 사용).

```jsx
{/* 1) 스타일 비교 열 4개 반복 */}
{variants.map(({ id, label, v }) => (
  <section key={v} aria-labelledby={id}>
    <h2 id={id}>{label}</h2>

    {/* 2) 각 열 안에서 메뉴 카드 반복 */}
    {DEMO_MENUS.map((item) => (
      <MenuCard
        key={item.name}
        name={item.name}
        price={item.price}
        variant={v}
      />
    ))}
  </section>
))}
```

**자습 가이드: 코드 주석을 어떻게 읽을까**

- 이 레슨의 핵심 파일(`App.jsx`, `Header.jsx`, `MenuCard.jsx`, `components/ui/card.jsx`, `components/ui/button.jsx`, `components/ui/input.jsx`, `components/ui/badge.jsx`, `components/ui/dropdown-menu.jsx`, `components/ui/dialog.jsx`)에는
  **“왜 이렇게 썼는지”** 를 설명하는 주석을 의도적으로 넣어 두었다.
- 자습할 때는 아래 순서로 읽으면 이해 속도가 빠르다.
  1. `App.jsx`에서 `variants`/`map` 구조를 먼저 보고, 네 열이 어떻게 생기는지 파악
  2. `Header.jsx`, `MenuCard.jsx`에서 같은 props가 `variant`에 따라 어떻게 분기되는지 비교
  3. `components/ui/card.jsx`에서 shadcn의 “조립형 컴포넌트” 구조 확인
  4. `components/ui/button.jsx`, `input.jsx`, `badge.jsx`, `dropdown-menu.jsx`에서 shadcn 조립형 패턴 확인
  5. `components/ui/dialog.jsx` + `ShadcnDialogDemo.jsx`에서 Radix 기능 결합 방식 확인

**자습 가이드: 화면에서 무엇을 관찰해야 하나**

- A열(일반 CSS): 가장 단순한 기준점(전역 클래스 기반)
- B열(CSS Modules): 강한 브랜딩 톤 + 파일 단위 스타일 분리
- C열(Tailwind): JSX 유틸 클래스 중심, 빠른 톤 실험
- D열(shadcn + Radix): 조립형 Card + Toolbar + 인터랙션 Dialog, 최신 SaaS 톤

- “D열에서 Card(정적)와 Dialog(인터랙션)의 구현 방식은 왜 다른가?”
- “D열 Toolbar에서 Button/Input/Badge/Dropdown이 왜 같은 톤으로 보이는가?”
- “A/B/C/D 중 내가 실무에서 먼저 선택할 전략은 무엇이고, 이유는 무엇인가?”

**왜 이렇게 설계했나 (교육 목적)**

- **같은 UI를 열마다 JSX를 통째로 복사해 두지 않고**, `title` / `subtitle` / `name` / `price` 같은 **데이터(props)는 한 번만** 넘기면 된다.
- 수강생이 **한 파일에서** “전역 CSS vs 모듈 vs 유틸”이 **DOM·클래스 문자열에 어떻게 반영되는지**를 나란히 비교하기 쉽다.
- 나중에 실무에서는 `variant` 대신 **테마**, **디자인 시스템 토큰**, **스타일 라이브러리** 등으로 확장하는 경우가 많다. 여기서는 그 **아이디어의 단순한 모형**으로 이해하면 된다.

**주의**

- `variant`에 **이 네 문자열 외의 값**을 넘기면, 컴포넌트는 기본 분기(`default`)와 같이 동작하도록 두었거나(또는 스타일이 어긋날 수 있으므로), 실습에서는 **표에 있는 값만** 쓰는 것이 안전하다.



### shadcn 실제 적용 가이드 (학습 박스)

아래는 **“로컬 UI 파일 보유 + import 사용”** 흐름을 실제로 적용하는 순서다.  
이번에는 `Card`(정적) + `Dialog`(인터랙션) 둘 다 넣어서, **Tailwind만 쓰는 부분과 Radix 기능이 결합되는 부분**을 한 번에 본다.

**1) 의존성 설치**

```bash
npm install clsx tailwind-merge @radix-ui/react-dialog
```

- `clsx` + `tailwind-merge`는 `cn()` 유틸에서 클래스 문자열을 안전하게 합칠 때 쓴다.
- `@radix-ui/react-dialog`는 모달의 접근성/포커스/키보드 동작을 담당하는 기능 라이브러리다.

<div style="background:#eef6ff; border:1px solid #c7ddff; border-radius:10px; padding:12px; margin:12px 0;">

**`cn()` 유틸 상세 설명 (흐름 분리 학습용)**

- `cn()`은 보통 `src/lib/utils.js`에 아래처럼 정의한다.

```js
import { clsx } from 'clsx'
import { twMerge } from 'tailwind-merge'

export function cn(...inputs) {
  return twMerge(clsx(inputs))
}
```

- `clsx` 역할: `false`, `null`, `undefined`를 자동으로 걸러서 **조건부 className**을 깔끔하게 합친다.
- `tailwind-merge` 역할: Tailwind 유틸이 충돌할 때 마지막 의도를 기준으로 **중복/충돌 클래스를 정리**한다.
- 즉 `cn()`은 "**조건부 결합 + Tailwind 충돌 정리**"를 한 번에 처리하는 shadcn 관용 유틸이다.

```js
// 예: 조건부 + 충돌 정리
cn(
  'px-2 py-1 text-sm',
  isActive && 'px-4 text-zinc-900',
  disabled && 'opacity-50'
)
// isActive=true면 결과는 px-4가 남고(px-2 제거), text-zinc-900이 적용됨
```

- 왜 필요한가?
  - 컴포넌트를 조합할수록 `className`이 길어지고, 같은 속성(`px-*`, `text-*`)이 중복되기 쉽다.
  - `cn()`을 쓰면 "기본 스타일 + 외부 전달 스타일"을 안전하게 합쳐 재사용 컴포넌트를 만들기 쉬워진다.

</div>

**2) Alias 설정 (`@/`)**

- `vite.config.js`에 alias를 넣어 `@`가 `src`를 가리키게 한다.
- `jsconfig.json`에도 경로 매핑을 넣어 에디터 자동완성/경로 인식을 맞춘다.

```js
// vite.config.js (핵심 부분)
resolve: {
  alias: {
    '@': fileURLToPath(new URL('./src', import.meta.url)),
  },
},
```

```json
// jsconfig.json
{
  "compilerOptions": {
    "baseUrl": ".",
    "paths": {
      "@/*": ["src/*"]
    }
  }
}
```

<div style="background:#f0f7ff; border:1px solid #c5daf0; border-radius:10px; padding:12px; margin:12px 0;">

**`vite.config.js`의 `import.meta.url`과 `@` alias 한 줄**

- `resolve.alias`의 `'@': fileURLToPath(new URL('./src', import.meta.url))`는 **Vite가 모듈을 해석할 때** `import … from '@/…'`를 **`프로젝트의 src` 폴더**로 연결해 주는 설정이다. (TypeScript에게 “프레임워크 쓰니까 타입 검사해라”는 신호가 **아니라**, **빌드 도구(Vite) 설정**이다.)
- **`import.meta.url`**  
  - ES 모듈에서 “**지금 이 파일(여기서는 `vite.config.js`)**”의 전체 URL(`file:///…/vite.config.js` 형태)을 가리킨다.  
  - “`vite.config.js`가 있는 폴더”라고만 말하면 부정확하고, **그 파일 자체의 URL**이 맞다.
- **`new URL('./src', import.meta.url)`**  
  - 위 URL을 **기준(base)** 으로 `./src`를 붙여, 결과적으로 **`vite.config.js`와 같은 디렉터리 아래의 `src`** 경로를 만든다.
- **`fileURLToPath(…)`**  
  - `file://` URL을 Node가 쓰는 **일반 파일 경로 문자열**로 바꾼다(Windows 등에서도 안전하게).
- **`defineConfig({ plugins: [react(), tailwindcss()], … })`**  
  - 객체 전체는 **Vite가 dev/build 시 읽는 설정**이다.  
  - `defineConfig`는 그 객체에 **타입 추론(IDE 편의)** 을 붙이는 헬퍼에 가깝고, `react()`·`tailwindcss()`는 **실제로 번들/CSS 파이프라인에 끼는 플러그인**이다.
- **`@`의 두 가지 의미 주의**  
  - `@/components/...`의 `@` → 이 프로젝트에서 설정한 **로컬 경로 alias**.  
  - `@radix-ui/react-dialog`의 `@` → npm 패키지 **스코프**이며, 위 alias와는 **다른 규칙**이다.

</div>

<div style="background:#f9f5ff; border:1px solid #ddcffc; border-radius:10px; padding:12px; margin:12px 0;">

**`components/ui` 폴더는 왜 쓰나? (관례 설명)**

- shadcn 프로젝트에서는 보통 `src/components/ui/*`에 `button`, `card`, `dialog` 같은 **재사용 UI 원자 컴포넌트**를 둔다.
- 반면 `src/components/*` 또는 `features/*`에는 화면/도메인 맥락을 가진 **앱 전용 컴포넌트**를 둔다.
- 즉 `ui`는 “디자인 시스템 부품함”에 가깝고, 앱 로직 컴포넌트와 분리해 관리하기 쉽다.
- 다만 이는 **강한 관례**이지 절대 규칙은 아니다. `components.json`의 alias 설정에 따라 `src/shared/ui/*`, `src/ui/*`처럼 바꿔도 된다.

**컴포넌트 폴더 최소 운영 규칙 (`src/components`)**

- 컴포넌트를 만들기 시작할 때는 `src/components`를 만들고, 최소 기준으로 `common`, `layout`, `feature` 3가지 성격으로 구분해 둘 수 있다.
- 다만 초반에는 과분류를 피하려고 **`common` + `layout`만 먼저** 두고 시작하는 것이 실무에서 관리가 쉽다.

**운영 규칙 4가지**

- 처음에는 단순하게 `common`, `layout` 폴더만 만든다.
- 같은 컴포넌트를 3번 이상 재사용하게 되면 `common`으로 옮긴다.
- 한 곳(특정 화면/도메인)에서만 쓰면 `feature` 아래로 이동한다.
- 파일명은 컴포넌트명과 동일하게 맞춘다. (예: `Button.jsx` 파일 안에 `Button` 컴포넌트)

```text
src/
   components/
      common/
         Button.jsx
         Input.jsx
      layout/
         Header.jsx
         MainLayout.jsx
      feature/          # 또는 도메인 이름(todo, auth 등)
         todo/
            TodoItem.jsx
            TodoList.jsx
```

**`components.json`은 왜 생기나?**

- 이 파일은 React/Vite 기본 파일이 아니라, **shadcn CLI가 참고하는 프로젝트 설정 파일**이다.
- 즉 “이 프로젝트에서 shadcn 컴포넌트를 어떤 규칙으로 생성/배치할지”를 적어 둔 메타 정보다.
- 그래서 shadcn을 도입하지 않으면 보통 필요 없다.

**현재 파일에서 중요한 항목**

- `"$schema"`: 설정 파일 형식을 검증하는 기준(에디터 자동완성/검증에 도움).
- `"style"`: shadcn 기본 스타일 프리셋(예: `new-york`).
- `"tailwind.css"`: Tailwind가 연결된 CSS 진입 파일 경로(여기서는 `src/index.css`).
- `"tailwind.baseColor"`: 기본 톤(여기서는 `zinc` 계열).

**`@radix-ui/react-dialog`에서 `@`는 무엇인가? (스코프 개념)**

- 여기서 `@`는 **로컬 경로 alias**가 아니라, npm 패키지 이름의 **스코프(scope)** 표기다.
- `@scope/package` 형태에서:
  - `@radix-ui` = 스코프(조직/퍼블리셔 네임스페이스)
  - `react-dialog` = 그 스코프 아래의 패키지 이름
- 의미는 쉽게 말해 패키지의 **“성(姓)+이름”** 이다.
  - 예: `react-dialog`만 있으면 이름 충돌 가능
  - 예: `@radix-ui/react-dialog`면 “radix-ui 계열의 react-dialog”로 구분 가능
- 이것은 **폴더 경로 개념이 아니라 패키지 식별자 규칙**이다.  
  설치 후에는 결과적으로 `node_modules/@radix-ui/react-dialog` 경로에 놓이지만, 본질은 “경로”가 아니라 “이름 규칙”이다.
- 주의: `@/components/ui/dialog`의 `@`는 우리가 설정한 **src alias**이고,  
  `@radix-ui/react-dialog`의 `@`는 npm **스코프**다. 모양은 같아도 의미가 다르다.

</div>

즉 shadcn은 항상 "Tailwind + Radix 100%"가 아니라,  
**컴포넌트 성격에 따라 Tailwind만 쓰기도 하고(Tailwind 중심), Tailwind + Radix를 같이 쓰기도 한다.**

### C. CSS Modules를 썼을 때 *비슷한* 모습

**1) 규칙은 `.module.css`에 직접 적음** (`Button.module.css` 예시)

```css
.primary {
  padding: 0.5rem 0.75rem;
  border-radius: 8px;
  border: 1px solid #cfc4b8;
}
```

**2) 그 스타일을 쓰는 컴포넌트에서 import** (`Button.jsx` 예시)

```jsx
import styles from './Button.module.css'

export default function Button() {
  return (
    <button type="button" className={styles.primary}>
      주문하기
    </button>
  )
}
```

빌드 후 브라우저에 나가는 HTML을 보면 `class` 값이 `Button_primary_xxxx`처럼 **파일마다 다른 고유 문자열**로 바뀌는 경우가 많습니다. 그게 **이름 격리**입니다.

**3) Vite에서 CSS Modules가 동작하는 방식 (오해 풀이)**

- **파일 이름:** Vite는 경로가 `***.module.css`** 형태이면 CSS Modules로 처리합니다. `**Button.jsx`와 파일명을 맞출 필요는 없습니다.** (`Card.jsx`에서 `import './Button.module.css'`처럼 다른 이름의 CSS를 가져와도 됩니다.)
- **무엇을 바꾸나:** 빌드는 주로 **그 `.module.css` 안에 적힌 선택자**(예: `.primary`)를 **모듈(파일) 단위로** 고유한 클래스 문자열로 바꿉니다. “JSX를 먼저 훑어서 쓰인 클래스만 남긴다”기보다, **CSS 모듈 파일을 기준으로** 이름이 정해지는 쪽에 가깝습니다.
- `**import styles`의 의미:** `styles`는 **원래 클래스 이름 → 변환된 문자열**을 담은 **JS 객체**입니다. JSX의 `className={styles.primary}`는 그 **매핑된 문자열**을 붙이는 것입니다.

컴포넌트는 관례상 `**src/components/`** 에 두는 경우가 많지만 규칙은 아닙니다. `App.jsx`만 쓰거나 `features/`, `pages/` 등으로 나누는 것도 흔합니다.

Vite 개발 서버는 `src/`·`index.html` 등 소스를 읽어 변환한 결과를 브라우저에 넘깁니다. 그래서 `dist`가 없어도 미리보기가 됩니다.

`**npm run build`** 를 실행할 때 `dist/` 가 생기며, 배포(프로덕션)에 올리는 빌드 결과에 해당하는 경우가 많습니다. 정적 호스팅이면 보통 `dist`만 올리면 되고, `node_modules`·원본 `src` 전체를 실행 서버에 꼭 같이 둘 필요는 없는 경우가 많습니다. (호스팅 방식에 따라 다름.)

로컬에서 빌드물만 확인할 때는 `**npm run preview`** 가 `**dist**` 를 기준으로 미리 보기에 쓰입니다.

# 1강 — HTML이 아니라 JSX, 그리고 컴포넌트

## 이번 강의에서 배우는 것

- React 앱이 브라우저에서 어떻게 시작되는지(`main.jsx` → `App.jsx`)
- **JSX**: JavaScript 안에서 UI를 트리 형태로 쓰는 문법
- **컴포넌트**: 화면을 함수 하나로 나누는 단위
- **props**: 부모가 자식에게 넘기는 입력값(이 강의에서는 “주입된 데이터”로만 사용)

## 왜 React인가? (이번 예제와 연결)

- **선언적 UI**: “DOM을 직접 만지기”보다 “이 데이터면 이렇게 그려라”에 가깝게 씁니다.
- **컴포넌트 재사용**: `MenuCard`를 두 번 쓰면, UI 규칙은 한 곳만 고치면 됩니다.
- **단방향 데이터 흐름**: 지금은 상태가 없지만, 앞으로는 “위에서 아래로 props가 내려간다”는 그림이 계속 이어집니다.

## 폴더/파일 역할


| 파일                            | 역할                                   |
| ----------------------------- | ------------------------------------ |
| `index.html`                  | 페이지에 `#root` div를 두고, 번들된 JS를 불러옵니다. |
| `src/main.jsx`                | `#root`에 React를 마운트합니다.              |
| `src/App.jsx`                 | 화면의 큰 뼈대를 만듭니다.                      |
| `src/components/Header.jsx`   | 제목/부제를 props로 받아 표시합니다.              |
| `src/components/MenuCard.jsx` | 메뉴 한 줄 UI를 재사용합니다.                   |


## JSX에서 자주 헷갈리는 것

- `**className`**: HTML의 `class` 대신 씁니다.
- **중괄호 `{ }`**: JS 표현식을 JSX 안에 끼워 넣을 때 사용합니다. (`{title}`처럼)
- **컴포넌트 이름은 대문자로 시작**: `<header>`(HTML 태그)와 `<Header>`(React 컴포넌트)는 다릅니다.

## props를 “읽기 전용”처럼 다루는 이유

React에서는 자식이 부모의 데이터를 함부로 바꾸지 않고, **부모가 내려준 값을 그리는 데 집중**하는 패턴이 기본입니다.  
(상태로 바꾸는 흐름은 2강부터 단계적으로 등장합니다.)
