# 6강 — 제어의 역전(IoC)과 서비스 컨테이너 (5강 이어서)

## 이번 강의에서 배우는 것

- **제어의 역전(Inversion of Control)** 이라는 말이 프론트엔드·React 맥락에서 무엇을 가리키는지
- “의존성을 컴포넌트 안에서 직접 만들지 않고 **밖에서 주입**한다”는 뜻
- 교육용으로 아주 작은 **서비스 컨테이너**(`register` / `resolve`)를 직접 구현해 본다
- React와 연결할 때 쓰는 **조립 루트(composition root)** 와 **Context API**
- 5강 `MenuPage`에 흩어져 있던 **저장소 로직**을 `menuRepository` 서비스로 분리한 예

---

## 5강과의 관계

- **화면 구조(URL, Layout, 페이지)** 는 5강과 동일한 흐름을 유지합니다.
- **달라지는 점**은 “메뉴를 어디에 저장할지, 사용자에게 어떻게 알릴지”를 `MenuPage`가 직접 `localStorage`/`console`에 붙지 않고, **미리 조립해 둔 객체**를 주입받는다는 것입니다.
- 이 강의는 **시리즈 확장**으로 읽을 수 있으며, 1~5강을 모두 들을 필요 없이 **5강을 마친 뒤** 바로 시작해도 됩니다.

---

## 1. “제어의 역전”을 이 강의에서 이렇게 쓴다

소프트웨어 공학 전반에서 IoC는 넓은 개념입니다. 여기서는 초보자가 따라가기 쉽게 **다음 한 문장**에 맞춥니다.

> **화면(컴포넌트)이 “구체적인 저장 방식·알림 방식”을 직접 고르지 않게 하고,**  
> **바깥(조립 루트)에서 구현체를 넣어 주면, 화면은 “무엇을 할지”에만 집중한다.**

비유로 자주 쓰는 말이 **할리우드 원칙**입니다.

- “내가 전화할게요( Don’t call us, we’ll call you )”  
- 컴포넌트가 `new LocalStorageSaver()`를 부르는 대신, **이미 만들어진 인터페이스에 가까운 객체**를 받아서 `load`/`save`만 호출합니다.

React만의 특징도 함께 기억하세요.

- **props로 부모가 내려주는 것**도 “바깥에서 주입”의 한 형태입니다.
- 이 강의에서는 **앱 전역에서 같은 구현을 쓰고 싶은 서비스**를 Context로 내려 보냅니다. (프롭 드릴링을 피하기 위함)

---

## 2. 왜 “컨테이너”라는 말을 쓰나

**컨테이너**는 “의존성을 담아 두었다가 필요할 때 꺼내 주는 상자”에 가깝게 비유했습니다.

이번 예제의 `ServiceContainer`는:

1. 문자열 **키**(예: `'menuRepository'`)로 무엇을 만들지 등록(`register`)하고
2. `resolve(키)`로 **실제 객체**를 돌려줍니다.
3. `singleton`이면 **한 번 만든 인스턴스를 재사용**합니다. (같은 저장소를 여러 번 만들지 않기 위함)

실무에서 쓰는 **대형 DI 프레임워크**와 비교하면 기능이 매우 적습니다. 대신 **동작 원리를 파일 하나로 읽을 수 있게** 의도적으로 줄였습니다.

---

## 3. 코드 읽는 순서 (추천)

아래 순서로 열어 보면 전체 그림이 잡힙니다.

1. `src/ioc/ServiceContainer.js` — `register` / `resolve` / singleton 캐시
2. `src/services/createMenuRepository.js` — 메뉴 JSON을 저장·로드하는 **역할** (localStorage는 여기 안에 캡슐화)
3. `src/services/createNotifier.js` — 콘솔에 메시지를 남기는 **역할** (나중에 토스트 UI로 바꿀 때 여기만 고치면 됨)
4. `src/ioc/createAppContainer.js` — 앱이 시작될 때 키를 등록하는 **조립 루트**
5. `src/main.jsx` — `createAppServices()`로 객체를 만든 뒤 `<AppServicesProvider value={services}>`로 React 트리에 심는다
6. `src/ioc/AppServicesContext.jsx` — `useAppServices()` 훅
7. `src/pages/MenuPage.jsx` — `useAppServices()`로 `menuRepository`, `notifier`를 받아 사용

---

## 4. React와의 접점: 조립 루트와 Context

### 조립 루트(composition root)

**“앱에서 딱 한 번, 의존성을 연결하는 장소”**를 조립 루트라고 부르는 경우가 많습니다.  
이 프로젝트에서는 `main.jsx`와 `createAppContainer.js`가 그 역할을 나눠 가집니다.

- `createAppServices()` 안에서만 `register`가 일어나도록 두면, **어디서 무엇이 만들어지는지** 찾기 쉽습니다.

### Context

`AppServicesProvider`는 **전역에서 공유해도 되는 서비스 객체**를 트리 아래로 전달합니다.

- 장점: `Layout`처럼 중간 컴포넌트가 `menuRepository`를 몰라도 된다(프롭 드릴링 완화).
- 주의: 무엇이든 Context에 넣으면 “편해 보이지만” **데이터 흐름이 암묵적**이 될 수 있어, **정말 공유할 값인지**를 나누는 습관이 필요합니다.

---

## 5. 5강 `MenuPage`와 무엇이 달라졌나

| 5강 | 6강 |
|-----|-----|
| 같은 파일 안에 `loadItemsFromStorage`, `STORAGE_KEY` 등이 있음 | `createMenuRepository`로 분리 |
| 화면에서 저장소 구현을 직접 알고 있음 | `menuRepository.loadAll` / `saveAll`만 앎 |
| 사용자 피드백이 암묵적(없거나 콘솔만) | `notifier.success(...)`로 명시 |

동작(추가·삭제·새로고침 후 유지)은 **사용자 입장에서 같아야** 합니다. 내부 구조만 “누가 제어하느냐”가 달라진 것입니다.

## 6. 실험 아이디어 (자습)

아래는 코드를 조금 만져 보며 IoC의 이점을 체감할 수 있는 과제입니다.

1. **Notifier 바꾸기**  
   `createNotifier`에서 `useAlert: true`로 바꿔 보면, `MenuPage`를 고치지 않고도 알림 UI를 바꿀 수 있습니다(교육용으로만 사용하세요).

2. **가짜 저장소로 테스트 상상하기**  
   `createMenuRepository({ storage: 가짜Storage })`처럼 **메모리 객체**를 넣으면, 브라우저 저장 없이 단위 테스트를 상상하기 쉽습니다. (이 저장소에는 테스트 파일까지 포함하지 않았습니다.)

3. **키 오타 내 보기**  
   `createAppContainer.js`에서 등록 키를 일부러 틀리게 해 보면, `resolve`가 던지는 오류 메시지로 **조립 단계의 실수**를 빨리 찾을 수 있습니다.

---

## 7. 한계와 “진짜” DI 도구에 대해

이번 `ServiceContainer`는:

- 의존성 그래프가 복잡할 때의 **자동 해석**, **생명주기**, **순환 의존성 처리** 등은 다루지 않습니다.
- TypeScript 없이 **키 문자열**로만 구분하므로, 오타는 런타임에서야 드러날 수 있습니다.

그래서 규모가 커지면 **도구나 타입 시스템**을 함께 쓰는 팀이 많습니다.  
하지만 **“바깥에서 주입한다”는 원리**는 동일합니다. 이 강의는 그 **원리를 손으로 한 번 밟아 본다**는 데 목적이 있습니다.

## 8. 6강 원리와 10강(실무에 가까운 조립)

> **참고:** 아래는 **6강 ↔ 10강 연결을 위한 요약**이다. 10강의 **전체 목차·실습·API 대응표**는 **`lesson-10-react-admin-ui/강의.md`** 에만 있다.

**조립 루트에서 의존성을 연결한다**는 원리는 그대로 두고, 구현만 바꾼 예가 **`lesson-10-react-admin-ui`** 에 있습니다.

| 6강 (교육용 IoC) | 10강 (같은 원리를 실무 스택으로) |
|------------------|----------------------------------|
| `ServiceContainer` + `AppServicesProvider` | **중앙 HTTP** (`httpClient.js`) + **TanStack Query**의 `QueryClientProvider` |
| `useAppServices()` 로 `menuRepository` | `useQuery` / `useMutation` + 얇은 `menuApi` 객체 |
| localStorage 뒤의 “저장소” | Spring API 뒤의 **서버 상태**(캐시·무효화는 Query가 담당) |

- **중앙 HTTP 클라이언트**: 베이스 URL·`Authorization`·JSON 처리 등을 `src/api/httpClient.js` 한곳에서 처리합니다(axios의 인터셉터와 비슷한 역할을 교육용으로 단순화한 것입니다).
- **TanStack Query**: 메뉴 목록처럼 **서버에서 온 데이터**는 `useQuery`로 가져오고, 추가·삭제는 `useMutation` 후 `invalidateQueries`로 목록을 다시 맞춥니다. 화면은 **로딩·에러·데이터 표시**에 가깝게 둡니다.
- 6강의 `AppServicesProvider`와 닮은 점은, **전역에서 한 번 준비한 것(HTTP 규칙·쿼리 캐시)** 을 트리 전체가 공유한다는 것입니다. 도구 이름만 서비스 컨테이너에서 Query로 바뀐다고 보면 됩니다.

**선택 확장(11강):** 테마·손님용 장바구니처럼 **서버 없이** 브라우저만 쓰는 전역 상태는 **`lesson-11-zustand-client-state`** 에서 **Zustand**로 다룹니다. “전역에서 꺼내 쓴다”는 점은 6강과 통하고, **서버 상태(10강)와 클라이언트 상태(11강)** 를 나누는 연습으로 이어집니다.
