# 11강 — Zustand로 클라이언트 전역 상태 (선택 확장)

> **이 문서가 어디에 있나요?**  
> 11강의 **전체 학습 안내**는 **이 파일**(`lesson-11-zustand-client-state/강의.md`)에 있다. 루트 `README.md`는 실행 요약이다.

이 강의는 **필수 시퀀스 밖**의 확장이다. 1~5강·7~10강을 거치지 않았어도 **5강(라우터)과 React 기본**만 있으면 따라올 수 있다.  
다만 **10강을 이미 본 사람**은 “서버 상태(TanStack Query)와 클라이언트 전역 상태를 어떻게 나누는가”를 비교하기 좋다.

---

## 1. 이번 강의에서 배우는 것

- **클라이언트 전역 상태**가 무엇인지, **서버 상태**(10강)와 어떻게 다른지 구분한다.
- **Zustand**로 전역 스토어를 만들고, 컴포넌트에서는 `useThemeStore`, `useCartStore`처럼 **훅만** 가져다 쓴다.
- **persist** 미들웨어로 `localStorage`에 저장해, **새로고침 후에도** 테마·장바구니가 유지되는 경험을 만든다.
- **partialize**로 직렬화할 필드만 골라, 불필요한 데이터나 함수 직렬화 문제를 피하는 습관을 본다.
- (참고) **Redux** 계열과 비교할 때 Zustand가 가진 **교육상의 이점**(보일러플레이트가 적음)을 이해한다.

---

## 2. 왜 “클라이언트 전역 상태”가 따로 필요한가

React만으로도 `useState`와 **state 끌어올리기**로 많은 것을 할 수 있다. 그러나 다음이 생기면 **전역 스토어**를 고려하는 팀이 많다.

- **깊은 트리**에서 같은 값(테마, 장바구니 수량)을 여러 컴포넌트가 써야 할 때 — props를 중간마다 넘기는 **프롭 드릴링**이 부담스러워진다.
- **라우트가 바뀌어도** 유지해야 하는 값(장바구니, UI 선호)이 있을 때 — 페이지 컴포넌트의 로컬 state만으로는 “앱 전체”와 맞추기 어렵다.

6강에서는 **Context + 서비스 객체**로 비슷한 문제를 풀었다. 11강은 **같은 “전역에서 꺼내 쓰기”**를 **Zustand**라는 작은 라이브러리로 구현한다.

---

## 3. 서버 상태 vs 클라이언트 상태 (이 강의의 기준)

| 구분 | 누가 진실인가 | 이 강의 예 |
|------|----------------|------------|
| **서버 상태** | DB·API가 최종 권위. 프론트는 캐시·동기화. | **10강** — 메뉴 목록을 Spring API에서 가져옴 |
| **클라이언트 상태** | 브라우저·앱 안에서만 의미가 있거나, 아직 서버에 안 보낸 값. | **11강** — 테마, **아직 주문 API가 없는** 장바구니 데모 |

장바구니는 실무에서는 결국 **서버에 주문**이 가므로 “진짜 진실”은 서버로 옮겨간다. 여기서는 **교육용**으로 서버 호출 없이 클라이언트에만 둔다. 나중에 10강 스택과 합치려면 “`addLine` 성공 후 `POST /api/cart`”처럼 **경계만 추가**하면 된다.

---

## 4. Redux 대신 Zustand를 예제로 쓴 이유 (초보자 관점)

- **Redux Toolkit**은 강력하지만, `configureStore`, `createSlice`, `Provider` 등 **개념 단위가 많아** 한 강에 넣기 부담이 될 수 있다.
- **Zustand**는 `create(() => ({ ... }))` 한 번으로 스토어가 생기고, **별도 Provider가 없어도** 모듈에서 import해 쓴다(내부적으로 싱글톤 스토어).
- 실무에서도 Zustand 채택 팀이 많다. Redux를 배우려면 공식 문서·별도 강의를 권장한다 — **이 강의 끝의 “다음에 읽을 것”** 참고.

---

## 5. 새로 등장하는 용어

| 용어 | 설명 |
|------|------|
| **전역 스토어** | 앱 어디서나 같은 인스턴스를 참조하는 상태 저장소. |
| **미들웨어(middleware)** | `persist`처럼 스토어를 감싸 저장·복원 등 부가 동작을 넣는다. |
| **리하이드레이션(rehydration)** | localStorage에서 읽은 JSON으로 스토어를 다시 채우는 과정. |
| **partialize** | persist할 **일부 필드만** 고른다. 함수는 JSON에 안 남으므로 보통 상태 데이터만 저장한다. |
| **셀렉터(selector)** | `useCartStore((s) => s.lines)`처럼 스토어에서 **필요한 조각만** 구독해 불필요한 리렌더를 줄인다. |

## 6. 코드 지도 (어떤 파일을 보나)

| 경로 | 역할 |
|------|------|
| `src/stores/useThemeStore.js` | 라이트/다크, `persist` + `partialize` |
| `src/stores/useCartStore.js` | 장바구니 줄 배열, 담기·빼기·삭제·비우기 |
| `src/components/ThemeSync.jsx` | `mode`가 바뀔 때 `document.documentElement.dataset.theme` 설정 → CSS 변수와 연결 |
| `src/components/Layout.jsx` | 테마 토글, 장바구니 **개수 배지**(스토어 구독) |
| `src/pages/ShopPage.jsx` | 카탈로그 정적 데이터 + `addLine` |
| `src/pages/CartPage.jsx` | `lines` 표시·수량 조절 |
| `src/data/catalog.js` | 판매 메뉴 목록(서버 없음) |

## 7. 따라 하기

1. `npm install` 후 `npm run dev`로 실행한다.
2. **메뉴 담기**에서 “담기”를 여러 번 눌러 상단 **장바구니 숫자**가 늘어나는지 본다.
3. **장바구니** 페이지에서 한 잔 빼기·삭제·비우기를 시험한다.
4. **다크** 버튼으로 테마를 바꾼 뒤, **페이지를 새로고침**해 테마와 장바구니가 유지되는지 확인한다.
5. 개발자 도구 → Application → Local Storage에서 `beanlog-theme-v1`, `beanlog-cart-v1` 키를 본다.

---

## 8. persist와 partialize를 조금만 더 깊게

- Zustand의 `persist`는 상태를 **JSON 문자열**로 바꿔 `localStorage`에 넣는다. 그래서 **함수**(addLine 등)는 저장되지 않는다. 재시작 시 스토어 정의에 있는 액션과 **저장된 필드**(예: `lines`)가 합쳐진다.
- `partialize: (state) => ({ lines: state.lines })`처럼 쓰면 **장바구니 데이터만** 저장한다는 의도가 분명해진다. 테마도 `mode`만 저장한다.
- 저장 키 이름(`name: 'beanlog-cart-v1'`)은 **다른 프로젝트·강과 겹치지 않게** 바꾸는 것이 좋다.

## 9. 막혔을 때

| 증상 | 확인할 것 |
|------|-----------|
| 새로고침 후 스타일만 이상하다 | `ThemeSync`가 마운트되는지, `index.css`에 `[data-theme='dark']` 변수가 있는지 |
| 장바구니가 비어 있다 | localStorage가 비활성화된 환경인지, 시크릿 모드 정책인지 |
| 배지가 안 바뀐다 | `Layout`에서 `useCartStore` 셀렉터가 맞는지, 다른 탭에서 storage 이벤트는 이 예제에서 다루지 않음(한 탭 기준) |

---

## 10. 6강·10강과 연결해 읽기

- **6강**: “바깥에서 조립해 넣는다”는 말을 **Context + 서비스**로 연습했다. 11강은 **모듈 스코프의 스토어**가 그 역할을 하며, Provider 없이도 **import 한 스토어는 항상 같은 인스턴스**다.
- **10강**: **서버 상태**는 TanStack Query + HTTP 클라이언트가 맡는 편이 일반적이다. **테마·임시 카트(클라이언트)** 는 Query 밖에서 Zustand 등으로 두는 **혼합**이 흔하다.
